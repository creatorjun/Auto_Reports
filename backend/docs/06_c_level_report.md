# C-Level 집중 관리 보고

## 화면과 저장

`/c-level-report`는 설계서의 처리 현황, 장기 미해결 고객사, SLA 위반 티켓을 제공합니다. 주간은 종료일 포함 7일, 월간은 선택 월 전체 또는 현재 월 누적입니다. URL의 `period=week|month`와 `date=YYYY-MM-DD`로 조회 조건을 유지합니다. 신규 메뉴 배지는 프런트엔드 빌드 변수 `VITE_CLEVEL_RELEASED_AT`부터 30일간 표시하며, 미설정 시 표시하지 않습니다.

요약 카드 클릭, 유형별 8개 기간 추이, 장기 이슈 1·3·6·12개월 필터, 고객사별 이슈 펼침, SLA 구분·유형 필터, 티켓 상세, Jira 원문 이동을 지원합니다. 상세의 처리 과정은 동일 상태에 재진입한 구간도 각각 표시합니다. 보고용 코멘트는 지연 원인, 조치 내용, 재발 방지·향후 계획과 보고서 포함 여부를 저장합니다.

보고서 히스토리에는 집계 수치, Jira 원본 이력, 집계 정책 버전, 보고용 코멘트, 저장자와 저장 시각을 함께 보관합니다. 저장한 보고서는 `/c-level-report/history/:id`에서 읽기 전용으로 열며, 이후 Jira나 코멘트가 바뀌어도 저장된 내용은 변경되지 않습니다. 기존 보고서 히스토리 화면에 C-Level 보고서 목록을 추가했습니다.

PDF는 기존 한글 글꼴·내보내기 어댑터를 사용한 A4 가로 문서이며 주요 섹션은 새 페이지에서 시작합니다. Excel은 전체 보고서 또는 고객사 표를 다운로드합니다. 현재 화면의 유형·장기 구간·SLA 필터를 파일에도 적용하고 표의 모든 대상 행을 포함합니다. 확인 불가 값은 문자열로, 확인된 수치는 숫자 셀로 저장합니다.

## 집계 계약

| 항목 | 기준 |
|---|---|
| 대상 유형 | 서비스 요청(단순문의), 인시던트, 개선. 현재 Jira 유형 분류를 사용하며 과거 유형 변경은 복원하지 않음 |
| 접수 | 조회 기간에 생성된 이슈 |
| 해결 | 조회 기간에 비완료에서 Done 범주로 전환한 이슈를 키로 중복 제거 |
| 미해결 | 기준시점 상태 범주가 Done이 아닌 잔량. `resolutiondate`로 대체하지 않음 |
| 해결률 | 해당 기간 접수 이슈 중 기준시점에 완료된 비율 |
| 평균 해결일 | 기간 내 해결 이슈의 생성부터 기간 내 마지막 Done 진입까지 달력 시간 평균 |
| 전기 비교 | 완료된 기간은 전체 비교, 진행 중인 기간은 전주의 같은 시각 또는 전월의 같은 일·시각까지 비교 |
| 추이 | 주간 8주 / 월간 8개월. 각 기간 종료시점의 미해결 잔량을 이력으로 복원 |
| 장기 구간 | 달력상 생성일의 1·3·6·12개월 경계. 12개월 이상 포함 |
| 고객사 수 | 확인된 고객사만 중복 제거. 고객사 미상 이슈는 이슈 수에는 포함 |
| SLA 신규 위반 | `breached=true`인 측정 주기의 `breachTime`이 조회 기간 안에 있음 |
| SLA 위반 건수 | 전체 티켓 수는 이슈 키 중복 제거, 최초응답·해결 건수는 측정 주기별 사건 수 |
| SLA 준수율 | 기간 내 완료 주기와 기간 내 이미 위반한 진행 주기 중 확인된 판정 비율. 아직 정상 진행 중인 주기나 데이터 누락을 준수로 계산하지 않음 |
| SLA 시간 | Jira가 계산한 목표·실소요·잔여 업무시간. 일시정지·업무 캘린더를 달력 시간으로 재계산하지 않음 |
| 상태 체류시간 | 상태 변경 이력의 달력 시간. 책임 구간 합계에서 완료 상태는 제외 |
| 지연 구간 | SLA 기한 도래 시점의 상태. 실제 원인이나 책임 확정으로 해석하지 않음 |

시간대는 KST이며 기간은 시작 포함·종료 제외입니다. 기준일이 과거이면 다음 날 00:00을 종료 경계로 사용합니다. 진행 중인 기간은 수집 시각이 종료 경계입니다. 월말 비교는 이전 월에 같은 일이 없으면 말일로 제한합니다.

## 확인 불가 처리

- Jira 값이 없거나 이력을 복원할 수 없으면 API는 해당 값을 `null`로 반환하고 UI와 파일에 **확인 불가**를 표시합니다. 확인된 0과 구분합니다.
- 상태 변경 이력을 모두 페이지 조회합니다. 이력 연결이 불완전하면 영향을 받는 과거 지표·구간 합계를 확인 불가로 처리하고 사유를 표시합니다. 일부 오래된 상태 범주만 불명확한 경우 확인 가능한 현재 상태까지 함께 포기하지 않습니다.
- 과거 기준시점 당시 진행 중이던 SLA 주기의 실소요·초과·일시정지 여부는 현재 값을 가져와 채우지 않습니다. 당시 SLA 정책이나 업무 캘린더를 재구성할 자료가 없으면 확인 불가입니다.
- 재오픈 횟수는 Done에서 비완료로 전환한 이력으로 계산합니다. 재오픈 이후 새로운 SLA 주기가 없으면 과거 완료 주기를 현재 SLA처럼 표시하지 않습니다.
- 최초응답은 해당 SLA 완료 시각을 우선 사용합니다. Jira 최초응답 차트 필드만 있는 경우 별도 출처와 확인 사항을 표시하며, 그 값으로 SLA 목표·위반 여부를 만들어 내지 않습니다.
- 고객사·파트너·보고자·담당자·TAC 담당자는 기준시점으로 복원 가능한 필드 이력을 적용합니다. 여러 자산 중 하나를 임의로 고르지 않습니다.
- 통신·권한·페이지 수집 실패는 정상적인 빈 결과로 숨기지 않고 조회 오류를 반환합니다.

## Jira 연동

기존 `JIRA_BASE_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, `PROJECT_KEY`, `SLA_INITIAL_RESPONSE_FIELD_ID`, `SLA_RESOLUTION_FIELD_ID`를 사용합니다. TACEA에서 확인한 메타데이터에 맞춰 다음 필드를 읽습니다.

| 데이터 | 필드 |
|---|---|
| 최초응답 / 해결 SLA | 기본 `customfield_12152` / `customfield_12151` |
| 고객사 | `customfield_11022` 텍스트, 비어 있으면 `customfield_10854` Assets |
| 파트너 | `customfield_10859` Assets |
| TAC 담당자 | `customfield_12522` 사용자 |
| 최초응답 보조 값 | `customfield_12454` |
| 지연 원인 / 책임 구분 원본 | `customfield_12051` / `customfield_12018` |

Jira 검색은 3개 대상 유형의 생성·해결·상태 변경 기간과 현재 미해결 조건을 함께 사용해 과거 잔량 복원에 필요한 후보를 수집합니다. 애플리케이션에서 정확한 기간 경계를 다시 적용합니다. 현재 프로젝트 상태 목록에 없는 과거 상태는 상태 ID API로 확인합니다. Assets 표시명도 권한 범위 안에서 조회합니다. Jira에는 쓰지 않으며 보고용 코멘트는 Auto_Reports DB에 저장합니다.

동시 Jira 요청은 6개로 제한합니다. 보고서 원본 조회 캐시는 120초, 이력 캐시는 이슈 키와 `updated` 기반 300초이며 크기를 제한합니다. 새로고침은 보고서 캐시를 우회합니다. 최초 조회는 이력 수에 따라 몇 분 걸릴 수 있습니다. 프런트엔드 조회 제한은 10분입니다.

## API와 저장 경계

모든 경로는 기존 인증이 적용된 `/api/v1` 하위입니다.

| 메서드·경로 | 동작 |
|---|---|
| `GET /c-level-report?period=week&date=2026-10-12&refresh=false` | 보고서와 서버 발급 `report_token` 조회 |
| `PUT /c-level-report/comments/{issue_key}` | `report_token`, 세 코멘트 필드, `included` 저장 |
| `POST /c-level-report/snapshots` | `report_token`, 선택적 `title`로 서버의 보고서 저장 |
| `GET /c-level-report/snapshots?limit=20&offset=0` | 저장 목록 조회 |
| `GET /c-level-report/snapshots/{id}` | 저장 시점 보고서 조회. 토큰은 반환하지 않음 |

코멘트 필드는 각각 10,000자, 제목은 200자까지입니다. 클라이언트가 집계 수치나 저장자를 지정할 수 없습니다. 토큰은 사용자별로 격리된 서버 메모리 미리보기를 가리키며 1시간 만료, 최대 16개입니다. 만료·퇴출·서버 재시작 후에는 410을 반환하므로 다시 조회해야 합니다. 현재 단일 백엔드 프로세스 구성에 맞추었으며 다중 프로세스/다중 복제본으로 확장하려면 공유 미리보기 저장소 또는 세션 고정이 필요합니다. 영구 저장된 스냅샷은 프로세스 재시작과 무관합니다.

코멘트와 스냅샷은 각각 DB 트랜잭션 안에서 저장 완료 후 응답합니다. 코멘트 커밋 이후 미리보기 만료가 발생해도 이미 성공한 저장을 실패로 응답하지 않습니다. 스냅샷은 사용자 입력 수치를 받지 않고 서버가 조회한 값과 당시 코멘트를 동결합니다.

## 아키텍처와 배포

Domain은 Jira 상태·SLA 측정 주기·코멘트·스냅샷 모델을 소유합니다. Application은 기간·이력·집계 정책과 조회/저장 유스케이스 및 포트를 소유합니다. Infrastructure는 Jira HTTP, Assets, 캐시, SQLAlchemy 구현을 소유하고 Presentation은 FastAPI 계약을 제공합니다. 모든 구현은 기존 `Container`에서 조립하고 HTTP·DB·캐시 수명은 종료 시 정리합니다. 기존 보고서 수집기와 SLA 대시보드 집계는 변경하지 않습니다.

Alembic `0015_add_c_level_reports`가 기존 테이블을 변경하지 않고 `c_level_comments`, `c_level_snapshots` 테이블을 추가합니다. 기존 컨테이너 시작 절차의 `alembic upgrade head`로 적용됩니다. 백엔드와 프런트엔드를 함께 다시 빌드합니다.

```bash
docker compose up -d --build
```

## 검증

```bash
cd backend
python -m unittest discover -s tests -v
python scripts/verify_c_level_jira.py --period week --date 2026-10-12

cd ../frontend
node --test tests/*.test.mjs
pnpm build
```

실제 Jira 검증 스크립트는 설정된 계정으로 읽기만 수행하고 중복·이력 구간·과거 SLA 값·누락 처리 계약을 확인합니다. `--output`은 내부 Jira 데이터를 포함한 보고서를 로컬 파일로 저장하므로 검증 파일은 Git에 포함하지 않습니다. 저장 API의 통합 검증은 운영 코멘트를 오염시키지 않도록 별도 DB에서 수행합니다.

2026-10-13 실제 Jira 조회에서 2026-10-06~10-12 주간 후보 276건, 접수 19건, 해결 22건, 미해결 111건을 확인했습니다. API 코멘트 저장, 스냅샷 조회, 이후 코멘트 수정으로부터의 불변성, 임의 수치 요청 거부를 격리된 PostgreSQL에서 확인했습니다. 이 결과는 당시 연결 계정의 조회 가능 범위 기준이며 이후 Jira 수정에 따라 재조회 결과는 달라질 수 있습니다.
