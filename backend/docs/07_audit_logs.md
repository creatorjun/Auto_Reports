# 관리자 감사로그

문서 기준: 2026-10-14 · 구현 커밋 `e280b75`.

## 계정 구분과 화면

`ADMIN`은 일반 사용자, `SUPERADMIN`은 관리자입니다. 환경 변수 이름을 바꾸지 않고 기존 로그인 흐름을 유지합니다. `SUPERADMIN=root`이면 root 계정으로 로그인했을 때만 사이드바와 모바일 메뉴에 **감사로그**가 나타납니다. 계정 이름은 하드코딩하지 않습니다.

`/audit-logs`에서 기간, 이벤트, 사용자, IP, 검색어를 조합해 최신순 기록을 조회하고 세부 필드를 펼쳐 볼 수 있습니다. 기록이 없는 상태와 파일을 읽지 못한 상태를 구분합니다. 사용자나 IP를 기록하지 않은 과거 항목은 **확인 불가**로 표시합니다. 조회 전용으로 수정·삭제 기능은 없습니다.

`/auth/me`의 서버 응답 `is_superadmin`으로 메뉴와 라우트를 제어합니다. 권한 정보가 없거나 조회에 실패하면 관리자 화면을 열지 않습니다. 로그인 변경 시 이전 사용자의 권한·감사로그 query를 재사용하지 않습니다. 직접 API를 호출해도 `require_superadmin`이 서명·만료·토큰 유형·관리자 세션과 설정된 계정 이름을 검사합니다. `ADMIN`은 403, 토큰 누락·위조·만료는 401입니다. `LOGIN=false`도 감사로그는 403입니다.

관리자 계정 이름과 비밀번호가 모두 설정되어야 하며 `ADMIN`과 같은 이름이면 관리자 권한을 부여하지 않습니다. 새 관리자 로그인은 기존 관리자 세션을 무효화하는 기존 정책을 유지합니다.

## 기록되는 작업

보고서 생성·삭제, 파일·폴더 작업의 감사 이벤트를 조회합니다. 일반 보고서 생성 요청은 `REPORT_TRIGGER`, SLA 생성은 `SLA_VIOLATION_REPORT_CREATE`, 수동 재배포 갱신은 `REDEPLOYMENT_REPORT_CREATE`로 구분합니다. 제거된 기능의 과거 감사 기록도 원래 이벤트 이름으로 계속 조회할 수 있습니다. 새 기록에는 인증된 작업 수행자를 함께 남깁니다. 로그인 성공 `LOGIN_SUCCESS`, 실패 `LOGIN_FAILED`, 로그아웃 `LOGOUT`도 기록합니다. 로그인 실패의 사용자 이름은 입력된 계정명이며 인증 성공을 뜻하지 않습니다. 이전 버전에서 기록하지 않은 작업·수행자 정보는 소급 생성하지 않습니다.

로거는 기존 텍스트 형식과 구분 가능한 JSON payload를 같은 `audit.log`에 기록합니다. 비밀번호·토큰·인증 헤더 등 민감 필드를 마스킹하고 개행을 이스케이프합니다. 파일 조회기는 이전 `EVENT | key=value` 형식과 새 구조화 기록을 함께 읽습니다. 로그에 저장하지 않은 비밀번호를 조회 API에서 복원할 수 없습니다.

## 저장과 조회

기본 저장 경로는 `AUDIT_LOG_DIR=logs`입니다. Docker Compose는 `/app/logs`를 `audit_logs` named volume에 연결하므로 컨테이너 재생성 후에도 기록이 남습니다. 자정 단위로 순환하고 기존과 같이 회전 파일 최대 90개를 보관합니다. 실제 보관 일수는 로그 발생·순환 시점에 따라 달라집니다.

조회 대상은 저장 경로의 `audit.log` 및 날짜가 붙은 회전 파일로 제한합니다. 클라이언트가 파일 경로를 선택할 수 없으며 심볼릭 링크는 제외합니다. 파일 읽기는 별도 스레드에서 수행하고 페이지에 필요한 최신 항목만 메모리에 보관합니다. 날짜 필터는 KST 기준으로 시작·종료일을 모두 포함합니다. 조회 시점의 파일 크기까지만 읽고 기록 중인 마지막 줄은 다음 조회에 표시합니다.

한 페이지는 최대 100건, 한 조건은 최대 100페이지를 지원합니다. 전체 일치 건수는 반환하며 더 오래된 기록은 날짜 범위를 나누어 조회합니다. 잘못된 줄과 길이 제한을 초과한 줄은 제외 사유를 표시합니다. 로그 디렉터리 접근 실패는 빈 목록으로 숨기지 않고 503을 반환합니다.

## 기존 컨테이너 로그의 최초 이전

이전 버전에서 별도 볼륨 없이 생성한 로그는 기존 컨테이너의 쓰기 계층에 있습니다. 컨테이너를 처음 재생성하기 전에 `/app/logs`를 백업하여 새 `audit_logs` 볼륨에 복사해야 합니다. `docker compose down`으로 이전 컨테이너를 먼저 제거하면 그 안의 로그를 잃을 수 있습니다. 이미 외부에 마운트된 로그는 기존 저장소를 계속 사용하거나 그 내용을 이전합니다.

기존 `tac_backend:/app/logs`를 별도 경로에 백업한 뒤 실제 Compose project 이름이 붙은 `audit_logs` 볼륨으로 복사합니다. `auto_reports_audit_logs`는 project 이름이 `auto_reports`인 경우의 예시입니다. 운영 환경이 다른 호스트라면 그 호스트의 기존 로그를 별도로 이전해야 합니다. 실제 계정 암호와 로컬 감사로그 백업은 Git에 포함하지 않습니다.

백업과 일반 배포 절차는 [운영 가이드](10_operations.md)를 참고하세요. 현재는 감사로그 화면을 위한 별도 DB 테이블을 사용하지 않습니다.

## 구현 경계와 검증

Domain의 `AuditLogQuery/Entry/Page`, Application의 `AuditLogReaderPort/AuditLogsUseCase`, Infrastructure의 파일 조회기·로거, Presentation의 관리자 의존성과 API로 책임을 분리합니다. `main.py`에서 조회기와 기록기가 동일한 저장 경로를 사용하도록 조립하며 파일 핸들러는 앱 종료 시 닫습니다. 인증된 작업 수행자는 요청 범위의 `RequestAudit`가 기존 기록 포트에 추가합니다.

```bash
cd backend
python -m unittest discover -s tests -v

cd ../frontend
node --test tests/*.test.mjs
pnpm build
```

권한 검증에는 일반 계정 거부, 관리자 허용, 비활성 로그인 거부, query token 거부, 이전 관리자 세션 거부를 포함합니다. 파일 조회 검증에는 기존 형식·새 형식, 날짜·검색·페이지, 순환 중 파일, 기록 중인 마지막 줄, 읽기 실패, 민감 필드 마스킹을 포함합니다.
