# 패키지 인벤토리 CVE 대응

문서 기준: 2026-10-28.

`/cve-response`는 서버에 등록한 `cve-inventory.json`의 패키지를 기준으로 **모든 버전의 공개 CVE**를 조회합니다. 첫 화면에는 회색톤으로 `Orcle Linux 8.10 / eyeCloudXoar 4.03_R2 기준`을 표시합니다. 파일에 기록된 버전의 영향 여부는 별도 정보이며 기본 목록을 제한하지 않습니다. 실제 프로세스에서 해당 라이브러리를 사용하는지까지 확인한 결과는 아닙니다.

## 수집과 식별

- 패키지명과 생태계가 검증된 Maven·npm 등의 패키지는 OSV에 버전 없이 조회합니다. 반환된 페이지 토큰을 끝까지 처리하며 최근 7일·최대 200건 제한을 적용하지 않습니다.
- Oracle Linux RPM은 Oracle Linux 8 공식 OVAL 피드의 패키지·CVE·수정 EVR을 연결합니다. 배포판 패치의 Epoch·Version·Release와 분기 조건을 보존하며 일반 라이브러리 버전과 혼용하지 않습니다.
- CVE 식별자가 없는 GHSA 등의 권고는 이 CVE 목록에서 제외합니다. 이후 CVE가 연결되면 다음 수집에 포함됩니다. 같은 패키지와 CVE의 중복 출처는 병합하고 영향 범위·수정 분기와 근거 링크를 보존합니다.
- 확인되지 않은 제품 이름·CPE를 유사 문자열만으로 확정하지 않습니다. 매핑이 없거나 수집에 실패한 패키지는 별도 조회 상태를 표시합니다. 성공적인 빈 조회는 해당 출처에서 등록된 CVE가 없다는 뜻이며 안전을 보장하지 않습니다.
- 외부 API에는 조회에 필요한 패키지 식별자·버전만 전달합니다. 원본 인벤토리의 내부 IP, 설치 경로, 원본 관측 내용을 외부 API나 공개 저장소에 전송하지 않습니다.

## 화면

- 기본 조건은 모든 버전·모든 위험도·전체 기간입니다. 치명적, 높음, 보통, 낮음, 미평가 필터와 검색·생태계·기록 버전 영향 여부를 조합할 수 있습니다.
- 목록은 패키지와 CVE의 조합을 한 행으로 표시합니다. 동일 CVE가 서로 다른 패키지에 해당하면 여러 행으로 표시되므로 목록 건수와 위험도 집계는 패키지별 CVE 건수입니다.
- 영향 버전과 수정 버전을 함께 표시하며 상세 영역에서 범위별 수정 버전과 출처를 확인합니다. 수정 버전이 명시되지 않은 항목은 미확인으로 유지합니다. Git 커밋 범위를 패키지 릴리스 버전으로 표시하지 않습니다.
- 등록 버전의 영향 여부는 `영향받음`, `영향받지 않음`, `확인 필요`로 구분합니다. 불명확한 버전, 조회 실패, 공급사 출처가 확인되지 않은 RPM은 영향 여부를 확정하지 않습니다.
- 패키지 조회 상태에서 조회 완료, 이전 자료, 조회 실패, 조회 대기, 매핑 필요를 확인할 수 있습니다. 일부 패키지의 매핑이 끝나지 않은 상태를 전체 인벤토리 점검 완료로 표현하지 않습니다.

## API와 갱신

로그인한 사용자만 다음 API를 사용할 수 있습니다. 응답은 `Cache-Control: no-store`로 제공합니다.

| API | 동작 |
|---|---|
| `GET /api/v1/cve-inventory` | 저장 자료의 검색·위험도·생태계·영향 여부 필터와 페이지 조회 |
| `GET /api/v1/cve-inventory/packages` | 패키지별 수집·매핑 상태 조회 |
| `POST /api/v1/cve-inventory/refresh` | 백그라운드 갱신 요청과 즉시 상태 응답 |

조회 API는 외부 취약점 수집을 시작하지 않습니다. 정기 갱신은 기본 2시간 간격이며 최초 수집이나 2시간이 지난 저장 자료의 갱신은 앱 시작 후 백그라운드에서 수행합니다. 재시작 시에도 남은 갱신 대기 시간을 유지합니다. 수집 작업은 제한된 동시성으로 실행하고 종료 시 취소·정리합니다. 기존 보안 뉴스의 매일 08:00 KST 수집과 번역 캐시는 독립적으로 유지합니다.

재조회는 신규 CVE뿐 아니라 기존 CVE의 패키지 연결·버전 범위 변경·철회도 반영합니다. CVE 공개일, 출처 수정일, 최초 확인 시각, 마지막 성공 수집 시각은 서로 다른 정보입니다. 수집 실패 시 해당 패키지의 마지막 정상 자료를 유지하고 이전 자료 상태를 표시합니다. 소스 등록 지연이나 식별자 매핑 누락까지 포함한 모든 CVE의 실시간 탐지를 보장하지 않습니다.

## 인벤토리 배치와 보존

원본 JSON은 Git에 넣지 않고 backend의 영구 볼륨 `/app/reports/cve-inventory.json`에 배치합니다. 사용자에게 받은 원본의 SHA-256을 별도로 확인해야 합니다. JSON의 `dataset_id`는 원본 XLSX의 해시이므로 JSON 파일 자체의 해시로 취급하면 안 됩니다.

```bash
docker cp /secure/path/cve-inventory.json tac_backend:/app/reports/cve-inventory.json
docker compose exec -T backend chmod 600 /app/reports/cve-inventory.json
docker compose exec -T backend sha256sum /app/reports/cve-inventory.json
```

파일 교체 전 기존 인벤토리와 CVE 스냅샷을 백업합니다. 수집 스냅샷은 보고서 영구 볼륨의 별도 SQLite 파일에 보존합니다. 배포 시 PostgreSQL·기존 보안 뉴스 SQLite·환경 설정·인증서를 보존하고 코드 변경 후 인증된 API와 실제 UI를 확인합니다.

인벤토리 내용이 바뀌면 동일한 패키지 식별자의 기존 CVE와 최초 확인 이력을 유지합니다. 새 수집이 끝날 때까지 이전 자료로 표시하고, 버전 정보가 달라졌을 수 있으므로 파일 버전의 영향 여부는 미확인으로 되돌립니다. 새로 매핑된 패키지는 조회 대기로 시작합니다. 변경된 인벤토리는 새 수집 대상으로 즉시 갱신할 수 있으며, 동일한 인벤토리의 재시작·수동 갱신에는 기존 2시간 대기 시간이 유지됩니다. 이 동작은 이전 데이터셋의 SQLite 스냅샷을 복원하는 경우에도 같습니다.

## 검증 범위

단위 테스트는 인벤토리 검증, 전 버전 조회, 페이지 누락 방지, CVE 중복 병합, 위험도 필터, 명시적 미확인 상태, 오류 시 이전 자료 보존과 API 인증을 확인합니다. 외부 API 호출 성공, 운영 배포, 실제 서버에서의 라이브러리 로딩·취약점 영향 확인은 각각 별도로 검증해야 합니다.
