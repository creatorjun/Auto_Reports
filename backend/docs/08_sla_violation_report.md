# SLA 위반 보고서

## 화면과 저장

대메뉴의 `SLA 위반`은 `대시보드` 바로 다음에 있습니다. `/sla-violations`에 진입하면 서버에 마지막으로 저장된 SLA 위반 보고서를 자동으로 표시합니다. 저장된 보고서가 없으면 생성 안내를 표시합니다.

주간·월간·연간 토글과 날짜 선택기로 생성 조건을 정한 뒤 보고서를 생성합니다. 조회에 성공한 결과는 히스토리에 자동으로 저장되므로 별도의 저장 버튼은 없습니다. 조건을 변경해도 이미 표시 중인 보고서의 기간이나 데이터는 바뀌지 않으며, 새 보고서 생성에 성공하면 교체합니다. 생성 중에는 조건과 생성 버튼을 비활성화하고 실패하면 이전 보고서를 유지합니다.

`최초응답 위반`과 `해결 위반` 목록을 각각 표시합니다. 각 목록의 건수는 티켓 수이며, 같은 SLA를 여러 번 위반한 티켓도 목록에서는 한 번 표시합니다. 두 SLA를 모두 위반한 티켓은 양쪽 목록에 나타나므로 두 건수의 합과 전체 고유 티켓 수는 다를 수 있습니다.

대시보드와 같은 필터에서 요청 유형·현재 상태·상반기/하반기를 선택하고 전체 선택·해제를 할 수 있습니다. 조건을 함께 선택하면 모두 일치하는 티켓만 양쪽 위반 목록에 표시하며, 목록의 건수도 즉시 다시 계산합니다. 필터는 보고서 생성이나 저장 내용을 변경하지 않습니다. 같은 화면에서 동일 보고서를 다시 조회하면 선택을 유지하고 다른 보고서로 바뀌면 초기화합니다.

요청 유형과 현재 상태는 보고서 생성 시 저장된 값을 사용합니다. SLA 보고서의 모든 요청 유형을 선택지로 제공하며, 확인할 수 없는 값은 `확인 불가`로 표시합니다. 요청 유형을 저장하지 않은 과거 보고서는 다시 생성하면 해당 정보를 확인할 수 있습니다. 과거 이력을 열 때 현재 Jira 값으로 덮어쓰지 않습니다. 상반기는 티켓 생성일의 KST 1~6월, 하반기는 7~12월이며 보고서 집계 기간 안의 티켓에 적용합니다. 연도 경계를 지나는 주간도 각 티켓의 생성월로 판정합니다.

티켓은 접힌 상태로 번호·제목·유형·생성일·경과일을 표시합니다. 유형은 인시던트·개선 등 Jira 요청 유형이며, 저장된 값이 없으면 `확인 불가`로 표시합니다. 업무 유형별·상태별로 기존 팔레트를 바탕으로 고유 색상 배지를 지정하며 대시보드 최신 이슈·상세 표에서도 같은 색상을 사용합니다. 행의 링크는 Jira 원문을 새 탭으로 열고, 별도의 펼치기 버튼은 페이지 이동 없이 상세 정보를 표시합니다. 상세에는 해당 SLA 위반 시각과 당시 상태, 상태별 누적 체류시간, 고객사·담당 파트너사·보고자·담당자·TAC 담당자·집계 시점의 현재 상태가 있습니다.

상태별 체류 기간에서는 `닫힘`과 같은 의미의 `닫혀`·`Closed` 항목을 표시하지 않습니다. 현재 상태나 SLA 위반 당시 상태가 닫힘인 경우에는 그 상태를 계속 표시합니다. 저장된 스냅샷과 경과일·위반 판정·집계는 변경하지 않으므로 기존 보고서에도 별도 생성 없이 적용됩니다.

상태별 시간 아래에는 한 줄 누적 막대로 체류 비율을 표시합니다. 닫힘을 제외한 표시 시간 합계를 100%로 계산하고 상태 배지와 같은 색상을 사용합니다. 각 시간 옆에도 비율을 표시하며 0.1% 미만은 `<0.1%`로 표기합니다. 합계가 0이거나 이력이 불완전한 경우에는 비율 막대를 표시하지 않습니다.

각 목록의 번호·제목·유형·생성일·경과일 컬럼명을 누르면 오름차순·내림차순을 번갈아 적용합니다. 번호는 숫자 부분을 고려하고 경과일은 숫자, 생성일은 실제 시각, 제목과 유형은 표시 문자열 기준으로 정렬합니다. 데스크톱에서 컬럼 사이 경계를 드래그하면 인접한 두 열의 너비를 조정합니다. 정렬과 너비는 최초응답·해결 목록별로 브라우저에 독립적으로 저장하며 필터 변경, 새로고침, 메뉴 재진입과 다른 보고서 조회 후에도 복원합니다. 저장된 보고서의 순서나 데이터는 바꾸지 않습니다. 설정은 같은 브라우저·사이트에서 유지되며 브라우저 저장소를 지우면 기본값으로 돌아갑니다. 저장소 사용이 차단되거나 저장값이 손상된 경우에도 기본값으로 화면을 사용할 수 있습니다.

기존 보고서 히스토리에서 SLA 위반 보고서 목록을 별도로 조회하고 `/sla-violations/history/:id`로 저장된 보고서를 다시 엽니다. 히스토리 조회는 Jira를 재수집하지 않으며 저장 당시의 값과 생성자·생성 시각을 유지합니다.

## 집계 기준

- 시간대는 `Asia/Seoul`입니다. 주간은 선택 날짜가 속한 월요일~일요일, 월간은 해당 달의 첫날~말일, 연간은 해당 연도의 1월 1일~12월 31일입니다.
- 범위의 시작 자정은 포함하고 다음 기간 시작 자정은 제외합니다. 날짜 판정은 티켓의 `created`를 KST로 변환한 뒤 수행합니다. 미래 날짜는 허용하지 않습니다.
- Jira 프로젝트에서 요청 유형과 현재 상태를 제한하지 않고 해당 기간에 생성된 티켓을 조회합니다. 최초응답 또는 해결 SLA의 `completedCycles`·`ongoingCycle` 중 `breached=true`가 있는 티켓을 수집합니다.
- 기간은 생성일을 선택하는 조건입니다. SLA 위반 여부와 상세 상태는 보고서 생성 시점 기준이며, 과거 기간의 마지막 날 당시 상태를 재현하는 보고서가 아닙니다. 선택한 기간 이후에 발생한 위반도 해당 티켓이 위반한 이력에 포함합니다.
- 정확한 위반 시각은 Jira의 `breachTime`을 사용합니다. SLA 근무시간·휴일·일시정지 규칙을 임의로 계산하거나 시작 시각에 목표 시간을 더해 위반 시각을 추정하지 않습니다.
- 상태 변경 이력은 전체 페이지를 읽고 연속성을 확인합니다. 같은 상태 ID의 이름이 번역·변경된 경우 ID를 기준으로 표시명을 통일하며, ID가 없으면 이름의 연속성을 확인합니다. 상태가 바뀐 시각에 위반했다면 새 상태를 사용합니다. 이력이 불완전하거나 정확한 위반 시각이 없으면 해당 상세를 `확인 불가`로 표시하고 티켓은 위반 목록에 유지합니다.
- 상태별 체류시간은 티켓 생성부터 보고서 생성까지 실제 경과시간을 합산합니다. 같은 상태로 돌아오면 합산하며, 근무시간·휴일·SLA 일시정지 시간을 차감한 SLA 시간과는 다릅니다.
- 경과일은 KST 기준 보고서 생성 날짜와 티켓 생성 날짜의 차이입니다. 이후 히스토리를 열어도 저장 당시 값은 유지합니다.
- 파트너 필드가 실제로 비어 있으면 `본사`, 파트너 지정 여부나 이름을 확인할 수 없으면 `확인 불가`입니다. 다른 미확인 인적·고객사 정보도 `확인 불가`로 표시합니다.

## Jira 필드와 오류 처리

| 항목 | 필드 |
|------|------|
| 최초응답 SLA | `SLA_INITIAL_RESPONSE_FIELD_ID`, 기본 `customfield_12152` |
| 해결 SLA | `SLA_RESOLUTION_FIELD_ID`, 기본 `customfield_12151` |
| 고객사 | `customfield_11022`, 비어 있으면 Assets `customfield_10854` |
| 담당 파트너사 | Assets `customfield_10859` |
| TAC 담당자 | `JIRA_RECENT_TAC_ASSIGNEE_FIELD_ID`, 기본 `customfield_12522` |
| 보고자·담당자 | `reporter`, `assignee` |
| 요청 유형 | `issuetype.name` |

티켓 검색과 상태 변경 이력은 모든 페이지를 조회하며, Jira HTTP 동시 요청은 최대 5개입니다. 통신·인증 실패나 잘린 검색 응답은 정상적인 빈 보고서로 저장하지 않습니다. 티켓별 데이터 누락과 불완전한 상태 이력은 보고서와 해당 티켓의 `warnings`로 표시합니다.

## API

모든 경로는 `/api/v1` 아래의 기존 인증 보호 라우트입니다.

| Method | Path | 요청·응답 |
|--------|------|----------|
| POST | `/sla-violations` | `{ "period": "week", "date": "2026-10-07" }`; 생성·저장 후 201과 전체 보고서 |
| GET | `/sla-violations/latest` | 마지막 저장 보고서 또는 `null` |
| GET | `/sla-violations/history?limit=20&offset=0` | 최신 생성순 요약 목록, limit 1~100·offset 0 이상 |
| GET | `/sla-violations/{id}` | 저장 보고서, 없으면 404 |

잘못된 기간·날짜는 422, 이미 생성 중이면 409, Jira 수집 실패는 502입니다. 읽기 응답은 `Cache-Control: no-store`이며, 생성에 성공하면 `SLA_VIOLATION_REPORT_CREATE` 감사 이벤트를 기록합니다. 프런트엔드 생성 요청은 최대 10분을 기다립니다.

티켓 응답의 `issue_type`은 문자열 또는 null입니다. 새 보고서는 요청 유형을 JSON payload에 함께 저장하며, 이전 payload에 필드가 없으면 null로 반환합니다. 이 추가 필드에는 DB 스키마 마이그레이션이 필요하지 않습니다.

## 저장 구조와 검증

Alembic `0017_add_sla_violation_reports`가 `sla_violation_reports` 테이블을 만듭니다. 기간·선택 날짜·생성 시각·생성자·고유 티켓 수·각 SLA 티켓 수와 상세 JSONB를 함께 저장합니다. 최신 조회는 `generated_at DESC, id DESC` 순서입니다. 일반·연간 보고서 테이블과 보존 정책은 변경하지 않습니다.

Domain은 보고서와 이력 모델, Application은 기간·상태 이력 계산과 생성·저장 유스케이스 및 포트를 소유합니다. Infrastructure는 Jira·Assets HTTP와 DB 직렬화를 맡고, Presentation은 인증·API·React UI를 담당합니다. HTTP 클라이언트와 생성 동시성 제어는 Container에서 조립하고 앱 종료 시 정리합니다.

```bash
cd backend
python -m unittest discover -s tests -p "test_sla_violation*.py" -v
cd ../frontend
pnpm test:sla-violations
pnpm build
```
